# 多 Agent 统一写入与外部套件同步规范（v1.4 复用契约）

> 本文档固化自用户确认的 **《四件套写入与同步规范总结（脱敏版）》**（依据：日历与提醒事项统一管理规范 v1.4、提醒事项写入与路由规范 v1.0、联系人身份核验规范）以及 **CRM 主控 + Google 套件官方 API 双线演进决议（2026-11-28）**，作为 `insurance-crm` 服务端、`/crm-mcp` 及所有接入 Agent（Antigravity/T3 Code、MUSE、Codex 等）的权威工程契约。
>
> **脱敏声明**：本文仅含规则、字段、模板与流程，不含任何真实客户信息、账号凭据或私密聊天记录。

---

## 0. 通用铁律（跨所有通道与 Agent 生效）

1. **人名直接写，不加分类前缀**：联系人、日历、提醒、CRM 笔记中的人名一律直接写，不加 `[客:]`、`[社:]` 等前缀。
2. **多客户场合才加人名前缀**：同一日期 / 同一场平台会涉及多位客户时，每条沟通记录前加 `[客户姓名]：`；一对一拜访不加人名前缀。
3. **日期唯一格式**：`YYYY-MM-DD`。生日标签统一用「生日」，不用「出生年月日」。
4. **标题严禁敏感明文**：日历标题与提醒标题会外显于锁屏 / 手表 / 通知中心，**严禁明文出现身份证号、银行卡号、保单具体金额、精确门牌号、敏感病史**。
5. **先读后写、写后重读**：写入前先实时查询并唯一锁定目标；写后必须重读核对，核对通过才汇报完成。
6. **同一事实不重复追加**：新事实只在对应日期条目下更新，不破坏历史。
7. **真实状态变化 vs 笔误**：真实状态变化保留历史并更新状态（如 `❌ 已取消参加`）；笔误定点纠正原记录。
8. **导入名单只是线索**：以实时 CRM / 实时通讯录记录为准，有出入先标记，不静默覆盖。

## 1. 联系人（Contacts：Google Contacts 稳态目标 / 既有 iCloud 过渡并行）

> **隐私墙移除说明（2026-11-28 用户明确决定）**：历史文档中“禁止身份证号进入外部联系人备注”的隐私墙规则已废止。外部联系人备注严格按 v1.4 §1.4 执行：**必须包含 `身份证号` 行（如有），但不写入保单件数、保费、跟进优先级、活动标签或 CRM 内部 ID**。

### 1.1 基础信息固定顺序与检索规则

每项单独一行，有哪项写哪项，没有的不留空行：

```text
姓名：[客户姓名]
性别：[男/女]
生日：[YYYY-MM-DD]
电话：[电话]
身份证号：[身份证号]
住宅地址：[地址]
工作地址：[地址]
```

- **找人优先按电话搜**：命中唯一则补缺基础行并保留原时间记录；未命中则新建；电话与姓名冲突或同名多条时停下确认，不盲写。
- **语音 / 转写 / 手写人名**：新建前须排查同音名及同事件上下文；无电话且无其他可识别信息的人名视为未确认草稿，不直接建档。
- **家庭卡来源**：只取主客户；生日只取卡面手写日期转 `YYYY-MM-DD`，**绝不凭身份证推导生日**；性别与身份证倒数第 2 位双向核验，冲突停下复核。

### 1.2 原生分组

- 确认为客户的联系人统一归入原生分组 / 标签组 **`客户`**。
- 严禁用备注文本或姓名前缀模拟分组；未经确认不得自行新建分组或改写既有分组归属。

### 1.3 备注（Notes）定版模板（v1.4 §3.4）

基础信息与时间记录之间以**一个空行**分隔，不写保单明细与 CRM 内部字段：

```text
姓名：[客户姓名]
性别：[女]
生日：[YYYY-MM-DD]
电话：[电话]
身份证号：[身份证号]
住宅地址：[地址]

[YYYY-MM-DD] [约定/交流事实，一行一条]
[YYYY-MM-DD] [约定/交流事实，一行一条]
```

### 1.4 写入与核对流程

- 新建 / 修改重要备注前先审草稿；写后重读同一条记录，**姓名 + 电话 + 备注内容**三项全对才报完成。
- 若误写到错误记录，须先恢复错改记录再修正正确记录，两条均重读核对。

## 2. 日历（Calendar：Google「工作」日历 + Google「生日 🎉」日历）

### 2.1 日历归属与时区

- **业务日程**：写入 **`工作`** 日历（过渡期既有 iCloud `工作` 并行，目标线切换为 Google `工作` 日历），必须显式携带 `calendar_id`、起止时刻与 `+08:00` 时区。
- **客户生日**：写入 Google 专用 **`生日 🎉`** 日历，标题统一为 `🎂 [客户姓名]的生日`；农历生日须换算为公历按年逐个创建并续建远期年份。
- 修改前按 `(日历 ID, 事件 ID, 标题, 人名)` 四元组唯一锁定，携带 `expected_etag` 防覆盖。

### 2.2 标题规范（16~24 字，无敏感明文）

- **一对一 / 业务拜访**：`[状态 Emoji] [业务 Emoji] 事项简述 - [客户姓名] (协同:[同事姓名])`
- **共享集体活动（平台会 / 私宴）**：`✅ 👥 [活动名称]`（标题不堆叠人名，取消时打 `❌` 保留历史不删除）

| Emoji | 业务类型 |
| :--- | :--- |
| `👥` | 平台会 / 集体说明会 |
| `🤝` | 初访 / 破冰拜访 |
| `📝` | 需求沟通 / 方案讲解 |
| `✍️` | 签约 / 合同确认 |
| `🛡️` | 保单服务 / 递送 / 理赔协助 |
| `☕` | 客情维护 / 随访 |

### 2.3 描述模板

**共享集体活动（平台会 / 私宴）：**

```text
活动信息
活动性质：[活动名称]
入场要求：[入场要求]

客户信息
姓名：[客户姓名]
电话：[电话]
客户状态：✅ 已确认 / 📨 已邀约 / ❌ 已取消参加

协同人员
带队负责人：[同事姓名]
协同服务：[同事姓名] ([负责事项])

沟通记录
[YYYY-MM-DD]
[客户姓名]：[沟通事实]
```

**一对一拜访：** 包含 `会面信息（目的/地点）`、`人员信息`、`沟通记录（不加人名前缀）`、`后续跟进`。会后事实追加到同一事件对应日期下，不另建重复事件。

## 3. 提醒事项 / 待办（Google Tasks 目标线 / 既有 iCloud Reminders 过渡并行）

### 3.1 四列表路由 v1.0（严格匹配名称，不擅自新建列表）

| 列表名称 | 英文键 | 定位与职责 | 默认状态 |
| :--- | :--- | :--- | :--- |
| **`收集箱 Inbox`** | `inbox` | 语意模糊、跨领域或待分类的全局兜底列表 | 全局默认兜底 |
| **`工作待办 Work`** | `work` | 客户拜访、保单检视、平台会邀约、方案沟通、回访及跨 Agent 协作 | **CRM 跟进默认目标** |
| **`个人生活 Personal`** | `personal` | 家庭事务、个人健康、账单、出行安排 | 个人私域 |
| **`日常采购 Shopping`** | `shopping` | 日用消费品补货、超市采购清单 | 购物清单 |

四级判定顺序：`显式指定 > 实体/关键词匹配 > 上下文继承（CRM 默认 Work） > 兜底 Inbox（附 [待分类]）`。

### 3.2 伴生提醒与不可重建铁律

- **重要拜访自动伴生 2 条提醒**：
  - 会面前 2 小时：`[客户姓名] 检查建议书与确认会面动向`
  - 会面当天 18:00：`[客户姓名] 回写跟进台账并归档资料`
- **用户亲手删除的提醒绝不自动重建**。

---

## 4. 沟通长记录与复盘笔记（CRM 原生沉淀）

- 鉴于外部备忘录桥曾出现“返回成功但未物理落库”的假通风险且移动端不可写，客户与平台会的详细沟通记录、复盘笔记**统一原生沉淀在 CRM PostgreSQL 数据库（`interactions` / 客户与活动档案）**，由 `/crm-mcp` 面向全 Agent 共享。

---

## 5. 双线并行、冲突与 UNKNOWN 停写铁律

1. **双线并行过渡**：过渡期保留既有 iCloud 同步链路不中断；新增 **Google 套件官方 API（People / Calendar / Tasks）** 独立开关并行验证，稳跑后再平滑切换。
2. **3-Way Diff 与 ETag 冲突**：基于 `BASE` 快照与 `expected_etag` 比对，遇 `CONFLICT` 立即中止写操作并转入冲突仲裁，绝不强行覆盖。
3. **UNKNOWN 停写铁律**：写操作超时或网络中断时状态置为 `UNKNOWN` 并停写，不得盲目重试；必须先通过两次列表读回确认为 `VERIFIED_NOT_APPLIED` 后才允许补发一次。
4. **诚实汇报**：绝不把兜底成功、缓存可读或单次读回当作原主通道写入成功。
